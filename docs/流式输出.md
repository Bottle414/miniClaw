# 流式输出

## 为什么做流式输出

LLM 生成长文本时，非流式模式下用户必须等待完整响应返回后才能看到任何输出。对 miniClaw 而言，这个问题在两个场景下尤为突出：

- **长文本生成**：一段推理或解释可能需要数秒才能完成，用户面对空白等待，感知延迟高
- **多轮工具调用**：ReAct 循环的典型场景，每轮迭代都是一次完整的 LLM 调用 + 工具执行，非流式模式下每轮都是"黑盒等待"

流式输出让文字逐 token 呈现、工具调用状态实时反馈，用户能立即看到 Agent 正在做什么，而不是等它做完才告诉结果。

## 概述

miniClaw 的流式输出通过事件协议驱动，让调用方无需等待完整响应即可实时接收 LLM 输出。两个工作流（旧循环、ReAct 循环）均已支持流式模式。

核心流程：

```
LLMRequest → adaptor.transformRequest() → DeepSeek API (stream: true)
  → SSE chunks → adaptor.transformStreamChunk() → RuntimeEvent
  → 消费端实时处理（逐 token 输出 / 工具状态展示）
  → createStreamMerger() 累积 → 完整 LLMAssistantMessage（用于工具执行）
```

## 开启流式输出

### 旧循环模式

通过环境变量 `STREAM` 或 `RuntimeConfig.stream` 控制。在 `createConfig()` 中默认为 `true`：

```
# .env
STREAM=true    # 开启流式（默认）
STREAM=false   # 关闭流式，使用 provider.chat() 非流式调用
```

旧循环根据此配置选择 `sendMessageLegacyStream()` 或 `sendMessageLegacy()`。

### ReAct 循环模式

ReAct 循环始终使用流式调用（`provider.chatStream()`），无需额外配置。流式事件通过 `onEvent` 回调传递，不传回调则不输出事件，但内部仍是流式调用。

```
# .env
USE_REACT_LOOP=true   # 启用 ReAct 循环（默认），自带流式输出
```

## 设计

### 事件协议分层

流式输出采用两层事件协议：

| 层级          | 类型         | 用途                                           | 定义位置                  |
| ------------- | ------------ | ---------------------------------------------- | ------------------------- |
| RuntimeEvent  | LLM 流式事件 | LLM API 逐 chunk 产出的原子事件                | `types/event/runtime-event.ts` |
| ReActEvent    | ReAct 循环事件 | 在 RuntimeEvent 基础上叠加循环层级事件         | `types/react/event.ts`    |

ReActEvent 包含 RuntimeEvent 的子集（跳过 `tool-result`，由 `react-tool-result` 代替）并新增 5 种循环层级事件，通过 `type` 字段前缀 `react-` 区分。

### 回调传递机制

ReAct 循环保持纯状态机设计，不直接做 I/O。流式事件通过 `ReActLoopConfig.onEvent` 回调传递给调用方：

```ts
interface ReActLoopConfig {
  provider: Provider
  config: Config
  userInput: string
  initialMessages?: LLMMessage[]
  onEvent?: (event: ReActEvent) => void  // 可选回调
}
```

- **传入 onEvent**：循环在关键节点调用回调，调用方实时消费事件
- **不传 onEvent**：行为与流式改造前完全一致，向后兼容

回调异常由内部 `emitEvent()` 函数 try-catch 包裹，不会中断循环执行。

## 事件类型

### RuntimeEvent（LLM 流式事件）

| 事件类型          | 字段                               | 说明                       |
| ----------------- | ---------------------------------- | -------------------------- |
| `text-delta`      | `delta: string`                    | 文本增量，逐 token 产出    |
| `tool-call-start` | `toolCallId`, `toolName`           | 工具调用开始               |
| `tool-call-delta` | `toolCallId`, `argumentsDelta`     | 工具参数增量（JSON 片段）  |
| `tool-call-end`   | `toolCallId`, `arguments`          | 工具调用结束，参数完整     |
| `tool-result`     | `toolCallId`, `result`, `success`  | 工具执行结果（runtime 产出） |
| `finish`          | `reason`, `usage?`                 | LLM 响应完成               |
| `error`           | `error: Error`                     | 错误                       |

> `tool-result` 由 runtime 执行工具后发出，非 LLM 直接产出。在 ReAct 循环中被 `react-tool-result` 代替，不会透传。

为什么这样设计：

- **text-delta 而非完整文本**：逐 token 产出让消费方能立即输出，而不是攒一批再显示
- **tool-call-start / delta / end 三段式**：拆分工具调用的生命周期——`start` 时可以展示"正在调用工具 X"，`delta` 时可以展示参数流（可选），`end` 时拿到完整参数触发工具执行。如果只有 start + end 两段，消费方在参数流式到达期间无法给出任何反馈
- **finish 携带 usage**：token 用量只在响应结束时才能统计，放在 finish 事件里自然合理
- **tool-result 与 tool-call 分离**：工具调用是 LLM 产出的事件，工具结果是 runtime 执行后产出的事件，两者发出者不同、时机不同，不应混在一起

### ReActEvent（ReAct 循环事件）

ReActEvent = RuntimeEvent 子集（6 种，不含 `tool-result`）+ 循环层级事件（5 种）：

| 事件类型               | 字段                                          | 说明               |
| ---------------------- | --------------------------------------------- | ------------------ |
| `text-delta`           | `delta`                                       | 透传               |
| `tool-call-start`      | `toolCallId`, `toolName`                      | 透传               |
| `tool-call-delta`      | `toolCallId`, `argumentsDelta`                | 透传               |
| `tool-call-end`        | `toolCallId`, `arguments`                     | 透传               |
| `finish`               | `reason`, `usage?`                            | 透传               |
| `error`                | `error`                                       | 透传               |
| `react-iteration-start`| `iteration`                                   | 迭代开始           |
| `react-phase-change`   | `phase`, `iteration`                          | 阶段转换           |
| `react-tool-execute`   | `toolCallId`, `toolName`                      | 工具开始执行       |
| `react-tool-result`    | `toolCallId`, `toolName`, `result`, `success` | 工具执行结果       |
| `react-loop-end`       | `reason`, `iterations`                        | 循环结束           |

`react-loop-end` 的 `reason` 取值：`"final_answer"` | `"iteration_limit"` | `"error"` | `"empty_response"`。

为什么需要 ReAct 层级事件：

- **react-iteration-start**：ReAct 循环可能多轮迭代，调用方需要知道当前是第几轮，才能输出"第 2 轮思考"这样的提示。仅透传 LLM 事件无法感知迭代边界
- **react-phase-change**：Think → Act → Observe → Decide 是 ReAct 的核心阶段模型，调用方据此展示不同的 UI 状态（如"正在推理..."、"正在执行工具..."）。没有这个事件，消费方只能靠猜测当前处于哪个阶段
- **react-tool-execute / react-tool-result**：工具执行不是瞬间完成的，拆成"开始执行"和"执行结果"两个事件，调用方可以在执行期间给出反馈，而不是等到所有工具跑完才一次性展示
- **react-loop-end**：循环终止有多种原因（最终答案、迭代限制、错误、空响应），调用方需要知道为什么结束，以便给出不同的提示
- **统一事件流而非两层事件流**：ReAct 事件和 LLM 事件在同一个 `onEvent` 回调中传递，调用方按 `type` 字段分发即可。如果分成两个流，消费方需要协调两个异步序列，复杂度更高
- **react- 前缀**：与 LLM 事件在 `type` 字段上天然区分，消费方不需要额外判断逻辑

## 适配层

### 流式适配方法

`LLMAdapter` 接口提供可选的 `transformStreamChunk()` 方法，将提供商 SSE chunk 转换为 RuntimeEvent：

```ts
interface LLMAdapter<TReq, TRes> {
  transformRequest(request: LLMRequest): TReq
  transformResponse(response: TRes): LLMResponse
  transformStreamChunk?(chunk: unknown): RuntimeEvent | RuntimeEvent[] | null
}
```

返回值：
- `RuntimeEvent` — 单个事件
- `RuntimeEvent[]` — 单个 chunk 产出多个事件（如同时包含文本增量和工具调用开始）
- `null` — 跳过无意义 chunk（如仅 `role: "assistant"` 的首帧）

### DeepSeek 流式适配

`deepseekAdapter.transformStreamChunk()` 的转换逻辑：

| SSE chunk 内容                 | 产出事件              | 说明                                  |
| ------------------------------ | --------------------- | ------------------------------------- |
| `finish_reason` 存在           | `finish`              | 包含 reason 和 usage                  |
| `delta.content` 存在           | `text-delta`          | 文本增量                              |
| `delta.tool_calls[i].id` + `function.name` | `tool-call-start` | 首个 chunk，同时将工具名中 `-` 还原为 `.` |
| `delta.tool_calls[i].function.arguments` | `tool-call-delta`   | 参数增量片段                          |
| 仅 `role` 声明的首帧           | `null`                | 跳过                                  |

> 工具名 `-` → `.` 还原在 `transformStreamChunk` 中完成，与 `parseToolCalls` 保持一致，其他层无需重复处理。

## 流式消息合并

### 问题

流式响应由多个 RuntimeEvent 组成，但工具执行需要完整的 `LLMAssistantMessage`（包含完整参数）。消息合并负责将事件流累积为完整消息。

### 两种合并方式

**1. 批量合并** — `mergeStreamMessage(events: RuntimeEvent[]): LLMAssistantMessage | null`

接收完整事件数组，仅当包含 `finish` 事件时返回完整消息，否则返回 `null`。

**2. 增量合并** — `createStreamMerger()`

创建有状态合并器，逐事件推送：

```ts
const merger = createStreamMerger()

for await (const event of provider.chatStream(req)) {
  merger.push(event)       // 累积
  // ... 实时消费 event
}

const message = merger.getMessage()  // 获取完整消息，未完成返回 null
```

### 合并逻辑

| 事件              | 累积行为                           |
| ----------------- | ---------------------------------- |
| `text-delta`      | 拼接 `content` 字符串              |
| `tool-call-start` | 新建工具调用条目（id, name）       |
| `tool-call-delta` | 追加 `arguments` 字符串            |
| `tool-call-end`   | 替换 `arguments` 为完整值          |
| `finish`          | 标记完成                           |
| `tool-result`     | 跳过（非 LLM 消息组成部分）        |
| `error`           | 跳过                               |

合并结果：

```ts
{
  role: "assistant",
  content: string | null,         // 文本内容（无则为 null）
  toolCalls: LLMToolCall[] | undefined  // 完整工具调用列表
}
```

## Provider 流式接口

`Provider` 接口提供两个并行方法：

```ts
interface Provider {
  init(config: Config): void
  chat(req: LLMRequest): Promise<LLMResponse>          // 非流式
  chatStream(req: LLMRequest): AsyncIterable<RuntimeEvent>  // 流式
}
```

### DeepSeek 流式实现

`DeepSeekProvider.chatStream()` 执行流程：

1. 转换请求：`deepseekAdapter.transformRequest(req)`
2. 调用 API：`client.chat.completions.create({ ..., stream: true })`
3. 逐 chunk 转换：`deepseekAdapter.transformStreamChunk(chunk)`
4. yield 每个事件：过滤 `null`，数组展开为单个事件

错误处理：API 异常时 yield `error` 事件而非抛出，保证消费方能正常结束迭代。

## ReAct 循环流式输出

### 事件发出时序

单次迭代的完整事件序列：

```
react-iteration-start   { iteration: N }
react-phase-change      { phase: "thinking", iteration: N }
react-phase-change      { phase: "acting", iteration: N }
  text-delta            { delta: "..." }        ← LLM 流式透传
  tool-call-start       { toolCallId, toolName } ← LLM 流式透传
  tool-call-delta       { ... }                 ← LLM 流式透传
  tool-call-end         { ... }                 ← LLM 流式透传
  finish                { reason, usage }        ← LLM 流式透传
react-phase-change      { phase: "observing", iteration: N }
  react-tool-execute    { toolCallId, toolName }
  react-tool-result     { toolCallId, toolName, result, success }
react-phase-change      { phase: "deciding", iteration: N }
react-loop-end          { reason, iterations }   ← 循环结束时
```

不带工具调用时，Act 阶段仅产出 `text-delta` + `finish`，然后直接进入 Decide。

### Act 阶段流式执行

`executeActPhase()` 使用 `provider.chatStream()` + `createStreamMerger()`，同时完成两件事：

1. **实时透传**：每个 RuntimeEvent（除 `tool-result`）通过 `onEvent` 传递给调用方
2. **累积合并**：每个事件推入 merger，流结束后 `getMessage()` 获取完整 `LLMAssistantMessage`

流式中断处理：若 `merger.getMessage()` 返回 `null`（未收到 `finish`），视为空响应，循环终止。

### Observe 阶段事件

工具执行事件与 RuntimeEvent 中的 `tool-result` 不同：

| 事件                | 发出者       | 包含 toolName | 用途                     |
| ------------------- | ------------ | ------------- | ------------------------ |
| `tool-result`       | Provider     | 否            | 旧循环工具结果           |
| `react-tool-execute`| ReAct loop   | 是            | 通知调用方工具开始执行   |
| `react-tool-result` | ReAct loop   | 是            | 通知调用方工具执行结果   |

ReAct 循环中，`tool-result` 事件被过滤不透传，改用携带 `toolName` 的 `react-tool-result`，让调用方无需从消息历史反查工具名。

## 消费端示例

### 旧循环流式消费（sendMessageLegacyStream）

```ts
const merger = createStreamMerger()

for await (const event of provider.chatStream(req)) {
  switch (event.type) {
    case "text-delta":
      process.stdout.write(event.delta)       // 逐 token 输出
      break
    case "tool-call-start":
      console.log(`\n[调用工具: ${event.toolName}]`)
      break
    case "error":
      console.error("\nError:", event.error.message)
      return
  }
  merger.push(event)
}

const message = merger.getMessage()
// 处理工具调用 → 递归 sendMessageLegacyStream()
```

### ReAct 循环流式消费（sendMessageReAct）

```ts
const result = await executeReActLoop({
  provider, config, userInput,
  initialMessages: messages,
  onEvent: (event) => {
    switch (event.type) {
      case "text-delta":
        process.stdout.write(event.delta)
        break
      case "tool-call-start":
        console.log(`\n[调用工具: ${event.toolName}]`)
        break
      case "react-iteration-start":
        if (event.iteration > 0)
          console.log(`\n--- 第 ${event.iteration + 1} 轮思考 ---`)
        break
      case "react-tool-execute":
        console.log(`  执行: ${event.toolName}...`)
        break
      case "react-tool-result":
        if (!event.success)
          console.log(`  失败: ${event.toolName} - ${event.result}`)
        break
      case "react-loop-end":
        if (event.reason !== "final_answer")
          console.log(`\n(循环结束: ${event.reason}, 共 ${event.iterations} 轮)`)
        break
    }
  }
})
```
