# Tool System 链路与设计

## 整体链路

```
注册: tools/weather.ts → handlerTool.register()
                              ↓
请求: handlerTool.getToolDefinitions() → LLMTool[]
       → adaptor.transformTools() (".→-") → DeepSeek API
                              ↓
响应: DeepSeek API → adaptor.parseToolCalls() ("-→.") → LLMToolCall[]
                              ↓
执行: handlerTool.call(name, params) → ToolResult
       → LLMToolMessage → 下一轮 LLM 调用
```

---

## 1. 工具定义与注册

每个工具在 `tools/` 下独立文件，导出 `{ definition, executor, metadata? }`：

```ts
// tools/weather.ts
export const weatherGetWeather = {
    definition: {
        name: "weather.getWeather",    // 统一使用 "." 分隔
        description: "获取指定城市的天气信息",
        parameters: { ... }
    } satisfies LLMTool,
    metadata: {
        category: "network",
        cacheable: true,
        readonly: true                 // 只读工具，同轮多个 toolCalls 可并行执行
    } satisfies ToolMetadata,
    executor: async (params: Record<string, unknown>, context: ToolExecutionContext): Promise<ToolResult> => { ... }
}
```

在 `createRuntime` 中通过 `createToolHandler` 创建实例并注册：

```ts
// index.ts (createRuntime 内)
const handlerTool = createToolHandler({
	sessionsRoot,
	onMetricsUpdate: options.onMetricsUpdate,
	onPermissionCheck: options.onPermissionCheck,
	permissionConfig: options.permissionConfig
})
handlerTool.register(weatherGetWeather.definition, weatherGetWeather.executor, weatherGetWeather.metadata)
handlerTool.register(timeGetCurrent.definition, timeGetCurrent.executor, timeGetCurrent.metadata)
handlerTool.register(fsReadFile.definition, fsReadFile.executor, fsReadFile.metadata)
handlerTool.register(mathCalculate.definition, mathCalculate.executor, mathCalculate.metadata)
```

当前注册的工具：

| 工具名               | 文件         | 类别    | readonly | 说明                   |
| -------------------- | ------------ | ------- | -------- | ---------------------- |
| `weather.getWeather` | `weather.ts` | network | true     | 获取指定城市的天气信息 |
| `time.getCurrent`    | `time.ts`    | system  | true     | 获取当前日期和时间     |
| `fs.readFile`        | `fs.ts`      | file    | true     | 读取指定路径的文件内容 |
| `math.calculate`     | `math.ts`    | compute | true     | 执行数学计算表达式     |

> `readonly` 字段决定同轮多个 `toolCalls` 是否并行执行，详见第 4 节。

`createToolHandler` 内部维护 `Map<name, ToolEntry>`，提供 `register` / `call` / `getToolDefinitions` 等方法。

**重要**: 工具处理器不再是全局单例，而是由 `createRuntime` 创建并注入到 ReAct 循环。`sessionsRoot` 参数用于 logging 中间件的文件输出路径，确保与 session 存储路径一致。Metrics 中间件通过 `onMetricsUpdate` 回调推送指标快照，不再直接写文件。

## 2. 请求阶段：工具定义 → Adaptor → API

```
handlerTool.getToolDefinitions()                // LLMTool[]
       ↓
provider.chatStream({ messages, model, tools }) // tools 传入 LLMRequest
       ↓
deepseekAdapter.transformRequest(req)           // 内部调用 transformTools()
       ↓
transformTools(): LLMTool[] → DeepSeekTool[]
  - 结构: { name, description, parameters } → { type: "function", function: { name, description, parameters } }
  - 命名转换: "." → "-"（weather.getWeather → weather-getWeather）
       ↓
OpenAI SDK 发送给 DeepSeek API
```

关键代码：`adaptor/deepseek/index.ts` → `transformTools()`

---

## 3. 响应阶段：API → Adaptor → 内部类型

### 流式场景（主流程）

```
DeepSeek 流式返回 delta.tool_calls
       ↓
deepseekAdapter.transformStreamChunk()
  - 首帧: tool-call-start 事件（含 id + name，name 中 "-" → "."）
  - 后续: tool-call-delta 事件（参数增量）
       ↓
StreamMerger 累积完整消息 → message.toolCalls: LLMToolCall[]
```

### 非流式场景

```
DeepSeek 返回 choice.message.tool_calls
       ↓
deepseekAdapter.transformResponse() → 内部调用 parseToolCalls()
  - 结构: { id, function: { name, arguments } } → { id, name, arguments }
  - 命名转换: "-" → "."（weather-getWeather → weather.getWeather）
```

关键代码：`adaptor/deepseek/index.ts` → `parseToolCalls()`

## 4. 执行阶段：ReAct Loop 中的 Act → Observe

在 `react/loop.ts` 中，工具执行嵌入 ReAct 循环。`toolHandler` 实例通过 `ReActLoopConfig` 注入，不依赖全局单例。

### Act 阶段 (`executeActPhase`)

- 从 `toolHandler.getToolDefinitions()` 获取工具列表
- 调用 `provider.chatStream()` 发送请求
- 流式合并得到完整 `LLMAssistantMessage`
- 检测 `message.toolCalls` 是否存在

### Observe 阶段 (`executeObservePhase`)

#### 并行执行策略

同轮多个 `toolCalls` 默认串行执行；当且仅当**所有** `toolCalls` 对应工具的 `metadata.readonly === true` 且 `toolCalls.length > 1` 时，使用 `Promise.allSettled` 并行执行：

- **并行路径**：先按原顺序 yield 所有 `tool-execute` 事件 → `Promise.allSettled` 并行执行 → 按原顺序 yield `tool-result` 事件
- **串行路径**（混合场景或单工具）：保留 `for...of` + `await`，每个工具完成后立即 yield `tool-result`
- **错误隔离**：单个工具异常（含 executor throw 和中间件链路未捕获 reject）不影响其他工具，转成统一的 `Error: xxx` 结果
- **依赖处理**：同轮 `toolCalls` 默认独立，跨轮依赖由 LLM 在下一轮决策（看到上轮结果后决定）

#### 执行步骤

- 遍历每个 `toolCall`（并行模式下一次性 map 启动）
- 调用 `toolHandler.call(name, params)` 执行工具
- 构造 `LLMToolMessage`（role: "tool", toolCallId, content=result）
- 添加到 `state.messages`，进入下一轮 ReAct 迭代

> 设计权衡：未显式声明 `readonly` 的工具默认走串行，是保守策略——避免未来新增写类工具意外并行导致竞态。新增写类工具时**不要**声明 `readonly: true`。

## 6. 事件流

工具执行过程中发出的事件：

| 事件类型          | 阶段          | 说明                                   |
| ----------------- | ------------- | -------------------------------------- |
| `tool-call-start` | LLM 流式响应  | 工具调用开始，含 toolCallId + toolName |
| `tool-call-delta` | LLM 流式响应  | 工具参数增量（JSON 片段）              |
| `tool-call-end`   | LLM 流式响应  | 工具调用结束，含完整参数               |
| `tool-execute`    | ReAct Observe | 工具开始执行                           |
| `tool-result`     | ReAct Observe | 工具执行结果                           |

## 7. 命名转换规则

命名转换 `.` ↔ `-` 完全封装在 adaptor 层，业务层始终使用 `.` 分隔的统一格式：

| 方向                  | 转换      | 位置                                          |
| --------------------- | --------- | --------------------------------------------- |
| 请求：内部 → DeepSeek | `.` → `-` | `transformTools()`                            |
| 响应：DeepSeek → 内部 | `-` → `.` | `parseToolCalls()` / `transformStreamChunk()` |

## 8. ToolHandler API

```ts
/** 工具执行上下文，传递给 executor 的运行时信息 */
interface ToolExecutionContext {
	/** 合并后的中止信号（parent + timeout） */
	abortSignal?: AbortSignal
}

/** 工具执行结果 */
interface ToolResult {
	content: string
	metadata?: Record<string, unknown>
	error?: {
		code: string
		message: string
	}
}

/** 异步工具执行函数类型 */
type ToolExecutor = (params: Record<string, unknown>, context: ToolExecutionContext) => Promise<ToolResult>

/** 工具元数据，基于 capability 声明中间件行为差异 */
interface ToolMetadata {
	/** 工具类别，仅用于描述和日志 */
	category?: "file" | "network" | "compute" | "system" | "browser" | "mcp"
	/** 是否可重试，默认 true */
	retryable?: boolean
	/** 最大重试次数，默认 0 */
	maxRetries?: number
	/** 重试间隔基数（ms），默认 1000，实际间隔 = base * 2^attempt */
	retryBaseDelay?: number
	/** 超时时间（ms），默认 30000 */
	timeoutMs?: number
	/** 所需权限点列表 */
	requiredPermissions?: string[]
	/** 是否可缓存，默认 false */
	cacheable?: boolean
	/** 缓存 key 生成策略，默认基于 toolName + stableStringify(params) */
	cacheKeyFn?: (params: Record<string, unknown>) => string
	/** 是否为危险操作，默认 false */
	dangerous?: boolean
	/**
	 * 是否为只读工具（无副作用，同轮多个 toolCalls 可安全并行执行），默认 false
	 * 未显式声明为 true 的工具在多工具调用时退化为串行执行
	 */
	readonly?: boolean
}

/** 工具处理器配置 */
interface ToolHandlerOptions {
	/** 权限配置 */
	permissionConfig?: PermissionConfig
	/** 权限确认回调 */
	onPermissionCheck?: (toolName: string) => Promise<boolean>
	/** 指标更新回调 */
	onMetricsUpdate?: (snapshot: MetricsSnapshot) => void
	/** session 根目录（用于 logging middleware） */
	sessionsRoot?: string
}

/** 创建工具处理器 */
function createToolHandler(options?: ToolHandlerOptions): ToolHandler

/** ToolHandler 实例方法 */
interface ToolHandler {
	/** 注册工具 */
	register(definition: LLMTool, executor: ToolExecutor, metadata?: ToolMetadata): void

	/** 设置/更新工具 */
	set(definition: LLMTool, executor: ToolExecutor, metadata?: ToolMetadata): void

	/** 通过名称获取工具 */
	get(name: string): ToolEntry | undefined

	/** 调用工具 */
	call(name: string, params: Record<string, unknown>, sessionId?: string): Promise<ToolResult>

	/** 获取所有工具定义 (LLMTool 格式) */
	getToolDefinitions(): LLMTool[]

	/** 是否已注册 */
	has(name: string): boolean
}
```

## 9. 权限系统

权限系统基于 `permission.json` 配置文件，支持 `allow`/`check`/`deny` 三级权限控制。

### 配置格式

项目根目录的 `permission.json`：

```json
{
	"allow": ["*"],
	"check": ["system.*"],
	"deny": ["system.shutdown"]
}
```

### 配置加载

通过 `loadPermissionConfig(rootDir)` 从指定目录同步读取 `permission.json`。调用方（TUI/Server）需显式传入 `projectRoot` 以确保从正确的目录加载：

```ts
import { loadPermissionConfig } from "@mini-claw/runtime"

const runtime = createRuntime({
	sessionsRoot: path.resolve(projectRoot, ".sessions"),
	permissionConfig: loadPermissionConfig(projectRoot)
	// ...
})
```

> **注意**：`loadPermissionConfig` 使用同步 I/O（`readFileSync`），因为 `createRuntime` 是同步工厂。文件不存在时返回默认配置 `{ allow: ["*"] }`，解析失败时抛错。

### 权限规则

- **deny**：匹配则直接拒绝，优先级最高
- **check**：匹配则调用 `onPermissionCheck` 回调请求确认
- **allow**：匹配则放行
- 未匹配任何规则时默认拒绝
- 通配符 `*` 匹配单层级工具名段（`weather.*` 匹配 `weather.getWeather`，不匹配 `weather.forecast.daily`）
- 单独的 `*` 匹配所有工具名

### 中间件链顺序

```
permission → cancellation → metrics → cache → logging → retry → timeout
```

- **permission**：权限检查（allow/check/deny）
- **cancellation**：请求取消支持，通过 `abortSignal` 传播
- **metrics**：运行时指标聚合（调用次数、耗时、错误率等），通过 `onMetricsUpdate` 回调推送
- **cache**：缓存层，基于 `toolName + stableStringify(params)` 生成缓存 key
- **logging**：日志记录，写入 `{sessionsRoot}/{sessionId}/tool-runs.json`
- **retry**：重试机制，支持指数退避（`base * 2^attempt`）
- **timeout**：超时控制，默认 30000ms

metrics 在 cache 之前，确保缓存命中时指标仍可记录。

## 10. 指标系统

Metrics 中间件仅负责运行时指标聚合，通过 `onMetricsUpdate` 回调向调用方推送指标快照。

### Runtime 侧

```ts
// createRuntime 传入 onMetricsUpdate 回调
const runtime = createRuntime({
	onMetricsUpdate: (snapshot) => {
		// 调用方处理指标快照
	}
})
```

### Server 侧持久化

Server 端在 `chat.service.ts` 中通过 `createMetricsWriter` 创建回调，将指标快照合并写入 `{sessionsRoot}/{sessionId}/metrics.json`：

```ts
// chat.service.ts
function createMetricsWriter(sessionsRoot: string, sessionId: string): (snapshot: MetricsSnapshot) => void {
	const metricsPath = path.join(sessionsRoot, sessionId, "metrics.json")
	return (snapshot) => {
		// 立即异步写入（fire-and-forget），写入前先读取已有数据合并
		mergeAndWriteMetrics(metricsPath, snapshot).catch(() => {})
	}
}
```

写入策略：

- 每次回调立即异步写入，不使用防抖定时器（避免定时器未执行导致数据丢失）
- 写入前先读取已有 `metrics.json`，用 `{ ...existing, ...snapshot.tools }` 合并
- 同一工具取新快照的累积值，不同工具保留已有数据

### Web 侧展示

Web 端通过 `GET /api/session/:id/metrics` 获取指标数据，在 Inspector 的 MetricsTab 中展示每个工具的调用次数、平均耗时、错误率、缓存命中率等。

### MetricsSnapshot 结构

```ts
type MetricsSnapshot = {
	tools: Record<string, ToolMetrics>
}
```
