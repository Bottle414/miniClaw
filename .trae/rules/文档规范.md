## 2. Prohibited APIs

### 2.1 禁止直接使用 LLM 提供商原生类型

项目已建立统一 LLM 类型层（`apps/runtime/src/types/llm/`），**禁止**在业务逻辑中直接引用 `openai` 包的类型（如 `OpenAI.Chat.Completions.ChatCompletion`）。

| 禁止                                | 应使用                             |
| ----------------------------------- | ---------------------------------- |
| `openai` 包的 Message 类型          | `LLMMessage` / `LLMUserMessage` 等 |
| `openai` 包的 Tool 类型             | `LLMTool` / `LLMToolChoice`        |
| `openai` 包的 Request/Response 类型 | `LLMRequest` / `LLMResponse`       |

所有提供商特定类型的转换必须在 **adaptor 层** 完成（参见 `apps/runtime/src/adaptor/deepseek/`）。

### 2.2 禁止绕过 ToolHandler 直接调用工具

工具注册和调用必须通过 `ToolHandler` 实例进行：

```ts
// 禁止
someFunction(params)

// 正确（在 createRuntime 内部）
handlerTool.call("weather.getWeather", params)
```

### 2.3 禁止在 runtime 中使用 CommonJS 语法

runtime 包 `"type": "module"`，必须使用 ESM：

```ts
// 禁止
const x = require("...")
module.exports = ...

// 正确
import x from "..."
export ...
```

### 2.4 禁止硬编码 API Key

API Key 必须通过 `.env` 文件 + `dotenv` 加载，禁止在源码中出现明文密钥。

### 2.6 禁止使用内联 import() 类型语法

类型注解中禁止使用 `import("...").Type` 内联导入语法，必须在文件顶部使用 `import type` 语句：

```ts
// 禁止
create(options?: import("../../memory/types").SessionCreateOptions): Promise<import("../../memory/types").Session>

// 正确
import type { SessionCreateOptions, Session } from "../../memory/types"
create(options?: SessionCreateOptions): Promise<Session>
```

### 2.5 禁止在 adaptor 外部处理工具名转换

工具名中 `.` 与 `-` 的互转逻辑封装在 `deepseekAdapter` 的 `transformTools` / `parseToolCalls` 中，禁止在其他位置重复实现此逻辑。

## 3. 运行原理

### Agent Loop

```
用户输入 → 构造 UserMessage → ReAct 循环
  → Think 阶段: 准备 LLM 调用
  → Act 阶段: provider.chatStream() → 解析响应
    → 有 toolCalls?
      → 是: Observe 阶段: 执行工具 → 记录观察结果 → Decide 阶段
      → 否: Decide 阶段: 检查终止条件
  → 应该终止?
    → 是: 返回最终答案
    → 否: 增加迭代次数 → 继续下一轮 Think
```

### 分层架构

```
createRuntime       → Runtime 工厂，返回 chat/sessionManager/config
  ├─ provider/      → LLM 提供商（封装 API 调用）
  ├─ adaptor/       → 统一类型 ↔ 提供商类型 转换
  ├─ react/         → ReAct 循环（Think-Act-Observe-Decide）
  ├─ tools/         → 工具注册与执行（createToolHandler 创建实例）
  ├─ memory/        → 记忆存储 / 上下文构建 / 摘要压缩
  ├─ types/llm/     → 统一 LLM 抽象类型
  ├─ types/event/   → ProviderEvent + RuntimeEvent 事件类型
  ├─ types/providers/ → 提供商特定类型
  └─ types/runtime  → RuntimeOptions, Runtime, ChatOptions
```

### 类型转换流向

```
业务代码 (LLMRequest/LLMMessage/LLMTool)
  → adaptor.transformRequest()
    → 提供商请求格式 (DeepSeekChatCompletionRequest)
      → API 调用
        → 提供商响应格式 (DeepSeekChatCompletionResponse)
          → adaptor.transformResponse()
            → 业务代码 (LLMResponse)
```

## 5. 代码约定

### 5.1 通用约定

- **TypeScript strict 模式** 已开启，禁止使用 `any`（历史代码除外，应逐步消除）
- **ESNext 模块**：`tsconfig.base.json` 配置 `"module": "ESNext"` + `"moduleResolution": "bundler"`
- **注释风格**：使用 JSDoc（`/** */`）为导出的函数、类、接口、类型添加文档注释，函数参数通常无需注释，但非显而易见的参数可加注释；内部逻辑说明使用行内注释（`//`）；多行使用 `/* */` 块注释作为文档
- **使用函数+闭包代替类**：在业务逻辑中，优先使用函数+闭包实现状态管理，避免使用类。例如：

```ts
// 禁止
class Counter {
	count = 0,
  increment = () => count++
}

// 正确
function createCounter() {
	let count = 0
	return {
		count,
		increment: () => count++
	}
}
```

- **解构赋值优先**：从同一对象读取多个字段时，必须使用解构赋值

```ts
// 禁止
const name = user.name
const age = user.age
const email = user.email

// 正确
const { name, age, email } = user
```

- **需求完成后更新文档**：每次完成需求后，必须同步更新 `docs/` 下对应的相关文档，确保文档与代码保持一致

### 5.2 Runtime 约定

- **统一类型优先**：新增 LLM 相关类型必须定义在 `types/llm/` 下，通过 adaptor 适配
- **工具注册模式**：新工具在 `tools/` 下创建文件，导出 `{ definition, executor }`，在 `createRuntime` 中通过 `handlerTool.register()` 注册
- **环境变量**：dotenv 加载由界面层（TUI）负责，runtime 不依赖 `process.env`；所有配置通过 `createRuntime(options)` 显式传入
- **使用内置日志函数**：打印日志必须使用 `utils/logger.ts` 的 `logger()` 函数，禁止直接使用 `console.log` / `console.error` 等（入口层面向用户的交互输出除外）。如 logger 不满足需求，应改造 logger 函数而非绕过
- **工具函数必须加单测**：`utils/` 下的工具函数必须编写单元测试；其他模块（memory、adaptor 等）选择性编写单元测试

### 5.3 Web 约定

- **组件 Props 有独立声明**：React 组件的 props 先用 `interface` 等声明

```ts
// 禁止
function App { { label }: { label: string } } {}

// 正确
interface ButtonProps {
	label: string
}

function App({ label }: ButtonProps) {}
/** 或者
 * function App(props: ButtonProps) {
 *  const { label } = props
 * }
*/
```

- **CSS 与组件分离**：样式必须与组件 TSX 分开编写，使用 CSS Modules 实现解耦。每个组件放一个文件夹，`index.tsx` 写组件逻辑，`index.module.css` 写样式：

```
components/
└── Button/
    ├── index.tsx
    └── index.module.css
```

```tsx
// Button/index.tsx
import styles from "./index.module.css"

interface ButtonProps {
	label: string
}

function Button({ label }: ButtonProps) {
	return <button className={styles.button}>{label}</button>
}
```

- **状态管理使用 Zustand**：全局状态使用 Zustand store，禁止使用 Context + useReducer 模式。Store 文件放在 `stores/` 目录下

- **Runtime Inspector 面板**：Inspector 组件位于 `components/Inspector/`，包含四个 Tab：
  - **Events** (`EventsTab`): 展示 ReAct 迭代时间线，每个阶段（Thinking/Acting/Observing/Deciding）包含详细内容（reasoning、text、toolCalls、terminationReason）
  - **Tools** (`ToolsTab`): 展示工具执行记录
  - **Metrics** (`MetricsTab`): 展示每个工具的调用指标（调用次数、平均耗时、错误率、缓存命中率等），数据从 `GET /api/session/:id/metrics` 获取
  - **Session** (`SessionTab`): 展示当前 session 信息

- **Runtime Store** (`stores/runtime-store.ts`): 管理 Inspector 展示所需的迭代、阶段、工具执行记录等数据。SSE 事件通过 `lib/runtime-event-processor.ts` 分发到 store。每次发送新消息时调用 `clearRuntime()` 清空数据

- **SSE 事件处理双通道**：SSE 事件同时由两个模块消费：
  - `lib/message-merger.ts`: 处理聊天消息合并（text-delta → 消息流）
  - `lib/runtime-event-processor.ts`: 处理 Runtime Inspector 数据（phase-change → 阶段记录、tool-execute → 工具记录等）

- **工具函数必须加单测**：`utils/` 下的工具函数必须编写单元测试

### 5.4 Server 约定

- **三层目录结构**：`apps/server/src/` 下分为三层，入口 `index.ts`、路由 `controller/`、服务 `service/`。controller 只负责路由和参数校验，调用 service 处理业务逻辑。service 不封装成类，导出单个函数即可：

```
src/
├── index.ts              → 入口，创建 Express 应用、挂载路由、启动服务
├── controller/
│   ├── chat.controller.ts → POST /api/chat 等路由处理
│   └── session.controller.ts → GET /api/sessions、GET /api/session/:id/metrics 等路由处理
├── service/
│   ├── chat.service.ts    → chat 业务逻辑（调用 runtime.chat 等）
│   └── session.service.ts → session 业务逻辑（调用 runtime.sessionManager 等）
└── __test__/
    ├── chat.controller.test.ts
    ├── session.controller.test.ts
    ├── chat.service.test.ts
    └── session.service.test.ts
```

```ts
// controller/chat.controller.ts — 只做路由
import type { Request, Response } from "express"
import { chatService } from "../service/chat.service"

export async function chatHandler(req: Request, res: Response) {
	const { message } = req.body
	// 参数校验
	if (!message || typeof message !== "string") {
		res.status(400).json({ error: "message is required" })
		return
	}
	// 委托 service
	await chatService(message, res)
}

// service/chat.service.ts — 业务逻辑
export async function chatService(message: string, res: Response) {
	// 调用 runtime、处理 SSE 流等
}
```

- **必须编写测试**：每个 controller 和 service 都必须有对应的测试文件，放在 `__test__/` 目录下。controller 测试使用 `supertest` 发 HTTP 请求，service 测试直接调用函数

- **Metrics 指标持久化**：Server 端通过 `createRuntime` 的 `onMetricsUpdate` 回调接收指标快照，合并写入 `{sessionsRoot}/{sessionId}/metrics.json`。写入策略为每次回调立即异步写入（fire-and-forget），写入前先读取已有数据合并，确保不同工具的指标不互相覆盖。`GET /api/session/:id/metrics` 端点读取该文件返回指标数据
