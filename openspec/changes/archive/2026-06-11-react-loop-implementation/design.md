## 背景

miniClaw 当前在 `apps/runtime/src/index.ts` 中实现了简单的递归消息循环。当 LLM 返回工具调用时，系统执行工具并递归调用 `sendMessage()` 获取下一次响应。这种模式在简单场景下可用，但缺少显式的推理结构，且难以：

1. 跟踪推理过程以供调试
2. 强制安全限制（迭代次数、token 预算）
3. 允许 LLM 显式决定何时停止
4. 分离编排、状态管理和终止逻辑的关注点

现有基础设施包括：

- Provider 层（`provider/deepseek.ts`）用于 LLM API 调用
- 适配层（`adaptor/deepseek/`）用于类型转换
- 工具注册中心（`tools/`）用于工具定义和执行
- 消息处理器（`utils/message.ts`、`utils/tool.ts`）用于工具执行

ReAct 模式通过 Think → Act → Observe → Decide 阶段使推理过程显式化，解决了这些局限性。

## 目标 / 非目标

**目标：**

- 实现显式 ReAct 循环，包含 Think-Act-Observe-Decide 阶段
- 使 LLM 能透明地推理多步任务
- 提供结构化终止条件（最终答案、迭代限制、错误）
- 保持与现有工具基础设施的向后兼容
- 同时支持工具调用和直接回答流程

**非目标：**

- 替换 provider 或 adaptor 层
- 更改工具执行机制
- 实现反思、规划或记忆管理等超出基本 ReAct 循环的高级功能
- 多 Agent 编排或对话模式

## 决策

### 决策 1：ReAct 循环架构

**选择：** 将编排（`react/loop.ts`）、状态（`react/state.ts`）和终止（`react/terminator.ts`）分离为独立模块。

**理由：**

- 单一职责：每个模块有明确的用途
- 可测试性：可独立对每个组件进行单元测试
- 可扩展性：易于添加新的终止条件或状态跟踪
- 可复用：状态和终止逻辑可被其他循环实现使用

**考虑的替代方案：**

- _单体循环函数_：可用但更难测试和扩展
- _基于类的设计_：对此用例而言过于复杂

### 决策 2：ReAct 阶段实现

**选择：** 将阶段建模为带结构化提示的显式状态转换。

**实现：**

```
THINK → (系统提示: "思考下一步该做什么")
ACT → (解析 LLM 响应中的工具调用或最终答案)
OBSERVE → (执行工具，收集结果)
DECIDE → (检查终止条件，继续或停止)
```

**理由：**

- 使每个阶段可检查和调试
- 允许按阶段定制提示
- 推理与执行的清晰分离

**考虑的替代方案：**

- _隐式阶段_：LLM 内部决定，无显式状态跟踪 — 更难调试
- _纯提示方法_：无状态跟踪，依赖 LLM 维护上下文 — 不够可靠

### 决策 3：终止逻辑

**选择：** 按优先级进行多级终止检查：

1. LLM 提供最终答案（无工具调用，有内容）
2. 达到迭代限制（可配置，默认 10）
3. 错误条件（API 失败、工具执行错误）
4. 空响应（边缘情况）

**理由：**

- LLM 对何时停止拥有主要控制权
- 安全限制防止无限循环
- 错误时优雅降级

**考虑的替代方案：**

- _仅迭代终止_：会截断合法的多步任务
- _Token 预算终止_：准确实现较复杂，迭代限制更简单有效

### 决策 4：状态管理

**选择：** 不可变状态对象，每次迭代更新。

**结构：**

```typescript
interface ReActState {
	iteration: number
	phase: "thinking" | "acting" | "observing" | "deciding"
	messages: LLMMessage[]
	actionHistory: ActionRecord[]
	observations: ObservationRecord[]
	shouldTerminate: boolean
	terminationReason?: string
}
```

**理由：**

- 可预测的状态转换
- 易于在任何时间点检查状态
- 支持未来功能如状态快照或回滚

**考虑的替代方案：**

- _可变状态对象_：更难跟踪变更和调试
- _全局状态_：使测试困难，引入隐藏依赖

### 决策 5：观察结构

**选择：** 结构化观察对象替代原始工具结果字符串。

**结构：**

```typescript
interface ObservationRecord {
	toolCallId: string
	toolName: string
	result: string
	success: boolean
	error?: string
	timestamp: number
}
```

**理由：**

- 提供关于调用了哪个工具的上下文
- 支持在观察层面进行错误处理
- 支持未来功能如结果缓存或重试逻辑

**考虑的替代方案：**

- _纯字符串观察_：丢失工具执行的元数据
- _完整工具调用对象_：冗余，我们只需要结果元数据

### 决策 6：消息历史策略

**选择：** 在状态中维护完整历史，但允许 provider 根据模型上下文窗口截断。

**实现：**

- 状态保留完整历史
- Provider 根据模型上下文窗口决定发送内容
- 为消息添加元数据以跟踪 ReAct 阶段

**理由：**

- 保留完整上下文供调试
- 允许灵活的上下文管理策略
- 无数据丢失

**考虑的替代方案：**

- _固定大小窗口_：可能丢失重要上下文
- _摘要化_：实现复杂，可能丢失细节

## 风险 / 权衡

**风险：显式推理导致 token 消耗增加**

- 缓解：使用简洁的 ReAct 阶段提示，允许配置禁用显式 Think 阶段

**风险：额外状态转换导致执行变慢**

- 缓解：状态转换是轻量的，开销极小。在实践中监控性能。

**风险：LLM 可能未正确遵循 ReAct 模式**

- 缓解：清晰的系统提示解释 ReAct 模式，验证响应，必要时回退到简单循环

**权衡：更复杂的代码库 vs. 更好的推理能力**

- 可接受：显式推理、可调试性和控制力的收益超过复杂性成本

**风险：破坏现有行为**

- 缓解：ReAct 循环仅替换主循环，其他层不变。使用现有工具充分测试。

## 迁移计划

### 阶段 1：并行实现

1. 实现 ReAct 模块，不修改现有 `index.ts`
2. 添加功能开关在旧循环和新循环之间切换
3. 使用现有工具和场景测试

### 阶段 2：逐步推出

1. 默认使用 ReAct 循环，允许回退到旧循环
2. 监控问题，收集反馈
3. 根据使用情况调整配置（迭代限制、提示）

### 阶段 3：完全迁移

1. 移除旧循环实现
2. 清理功能开关
3. 更新文档

**回滚策略：**

- 功能开关允许即时切换回旧循环
- 无数据库或持久状态变更，回滚很简单

## 待解决问题

1. 是否应在 "Think" 之前添加 "Plan" 阶段用于复杂任务？
   - 推迟到获得实际使用数据后再决定

2. 长时间运行的循环中，观察结果是否应被摘要或压缩？
   - 先使用完整观察，如果 token 使用量有问题再优化

3. 是否应支持工具的自定义终止条件？
   - 可能的未来增强，不在初始实现中

4. 如何处理多步计划中间的工具执行失败？
   - 让 LLM 观察错误并决定下一步（重试、替代方案、放弃）
